## Critical findings

### 1. `state_seat_fp.js` VIC data is corrupt and live in the model

`webapp/src/data/state_seat_fp.js` (auto-generated by
`scripts/generate_state_seat_fp.py`) classifies **every one of the 87 VIC
districts as `ind: 100.0`** with ALP/Coalition/Greens all 0.0:

```js
1: { alp: 0.0, coal: 0.0, grn: 0.0, ind: 100.0, on: 0.0, other: 0.0 },  // Albert Park
```

`computeModelledSeatsVic()` (App.jsx:3168) uses the per-seat FP baseline
whenever `seatFpMap?.[seat.id]` exists — which it does for all 87 seats — so
the live VIC model is consuming this garbage. The CI regeneration on 2026-06-01
reproduced the identical output ("Wrote … (1 states)", `git diff` clean), so the
bug is deterministic in the VEC parse → `{state}_district_fp` → `classify_party`
path (every candidate's `party_ab` resolves to neither ALP/coal/GRN — likely the
join or `vec_parse._guess_party_ab` leaves `party_ab` unusable, and everything
lands in one bucket).

**Fix:** debug `generate_state_seat_fp.get_district_fp()` against the VIC DB
(rebuildable locally from the LFS Excel files), assert sane output (e.g. ALP+coal
share > 50% statewide) before writing the module, and add a guard in the
generator that refuses to overwrite good data with degenerate data.

### 2. `update-model-constants.yml` has never succeeded — and nobody noticed

Both scheduled runs failed (2026-05-01, 2026-06-01). The June log shows
`compute_seat_residuals.py:91 KeyError: 'name'` — the script expected `name`
but `pipeline/export.py` emits `division_name`. Commit `e78d326` (2026-06-10,
"Fix never-run generator scripts…") fixed that locally, but the fix has not been
exercised in CI; the next scheduled attempt is 2026-07-01.

Additional problems in the same workflow:

- `data/seat_demo_mult.json` does not exist in the repo, yet the commit step
  diffs/adds it. `git diff --quiet` **ignores untracked files**, so on the first
  successful run the newly created file will be invisible to the change check
  (and if it's the only change, the job will wrongly say "Nothing changed").
- The DB cache is configured for `data/elections.db`, but `pipeline/config.py:108`
  sets `DB_PATH = data/aec_elections.db`. The post-job log confirms: *"Path
  Validation Error: Path(s) … do(es) not exist, hence no cache is being saved."*
  Result: the full AEC dataset for 2016/2019/2022/2025 is re-downloaded from
  results.aec.gov.au every month for nothing.

**Fix:** trigger a `workflow_dispatch` run now to validate the June 10 fix;
change the cache `path` to `data/aec_elections.db` (both monthly workflows);
replace the change check with `git add <files> && git diff --cached --quiet`.

### 3. `generate-state-fp.yml` is a no-op that reports success

The 2026-06-01 "successful" run completed all 8 state pipelines in 17 seconds.
The logs show why: every state electoral commission download fails in CI
(ACT EC returns **403 Forbidden** to the runner; NSW/QLD/WA/SA/NT/TAS find no
files), `main.py` logs `ERROR` but exits 0, and the module is regenerated with
7 empty placeholder objects + the corrupt VIC data. Only VIC "works" because its
raw Excel files are committed via LFS.

Also:

- Same wrong cache path as above (`data/elections.db` vs `data/aec_elections.db`).
- `main.py --state X` already regenerates `state_seat_fp.js` at the end of every
  state run, so the workflow regenerates the module 9 times per run.
- **SA naming mismatch:** the generator exports `SA_SEAT_FP_2022`, but App.jsx:642
  reads `STATE_SEAT_FP.SA_SEAT_FP_2026` — SA always falls back to `{}` even if
  the data existed.

**Fix:** state election results are static between elections — there is nothing
for a monthly cron to pick up. Drop the `schedule:` trigger and keep
`workflow_dispatch` for after each state election / parser change. Make state
pipeline failures fail the job (propagate a non-zero exit from `main.py`, or
grep the log for `ERROR`), so a "green" run actually means data was loaded.
Fix the SA constant name on whichever side is wrong (the SA election is
2026-03-21, so the upcoming baseline year needs deciding deliberately).

### 4. Auto-updated data may never reach the deployed site

`CLAUDE.md`/`README` say GitHub Pages builds on every push to `main` via GitHub
Actions — but there is **no deploy workflow in `.github/workflows/`**, no
`gh-pages` branch, and nothing was ever deleted from git history. Meanwhile the
poll and state-FP auto-commits are tagged `[skip ci]`, which Vercel's Git
integration also honours. So depending on which host actually serves the site,
weekly poll updates may be committed to `main` but never deployed — a failure
mode that has already occurred once (commit "Fix polls not updating on site").

**Fix:** confirm the deployment path. If GitHub Pages: add the missing
build-and-deploy workflow and remove `[skip ci]` from data commits (or trigger
the deploy with `workflow_run`). If Vercel: drop `[skip ci]` from the commit
messages and instead prevent workflow recursion with `paths-ignore` /
`if: github.actor != 'github-actions[bot]'` guards.

## Significant findings

### 5. Betting odds have been "manual placeholder" the whole time

`data/polls/betting_odds.json` has `"source": "manual"`. The daily job's months
of "chore: auto-refresh betting odds" commits were re-stamping the manual
placeholder with the current date until the 2026-06-09 honesty fix; since then
the job is a daily no-op. Neither Betfair nor The Odds API has ever returned
data, meaning the secrets are missing, empty, or expired. Note that
`BETFAIR_SESSION_TOKEN` is inherently unsuitable as a long-lived secret —
Betfair session tokens expire within hours/days; a real integration needs the
login endpoint (cert or interactive) inside the job to mint a fresh token.

**Fix:** either configure a working `ODDS_API_KEY` (simplest), implement Betfair
login in `pipeline/betting_odds.py`, or reduce the schedule to weekly until a
live source exists. Add a visible warning when the job falls back to manual
(e.g. step summary or failing soft-check) so "running but serving placeholder"
is distinguishable from "working".

### 6. VIC poll scraping has produced nothing since February

`data/polls/vic_polls.json`'s newest poll is dated **2026-02-16**, despite weekly
scrapes of the Wikipedia page for the November 2026 VIC election. Either the
page's table format changed (the parser soft-fails per design), all newer
pollsters fail `normalise_pollster()`, or genuinely no polls were published —
worth verifying manually, because the soft-fail design makes all three look
identical. Related: `update-polls.yml` copies `vic_aggregated.json` to
`webapp/src/data/` but never `git add`s it, and nothing in the webapp imports
it — the VIC aggregation never reaches the site at all.

**Fix:** run `python scripts/update_poll_inputs.py -v --dry-run` locally and
inspect; add a staleness check to the workflow (warn when the newest VIC poll is
> N weeks old). Then either import `vic_aggregated.json` in the frontend and add
it to the commit step, or delete the dead copy step.

### 7. Hand-maintained state polls have two diverging copies

`nsw/qld/sa/wa_polls.json` exist in both `data/polls/` (last touched 2026-05-11)
and `webapp/src/data/` (edited directly on 2026-06-10). App.jsx imports the
webapp copies, so `data/polls/` is a stale decoy that any future automation
(or contributor) might "helpfully" copy over the newer data.

**Fix:** pick one source of truth — keep the canonical files in `data/polls/`
and make the workflow copy them over (matching the aggregated.json pattern), or
delete the `data/polls/` copies.

### 8. `economics.json` and `leaders.json` have fetchers but no schedule

`pipeline/fetch_economics.py` (ABS CPI, unemployment, RBA cash rate — inputs to
the incumbent-vote model) exists and even handles the webapp copy itself, but no
workflow calls it; the data is stamped 2026-04-02. `leaders.json` (2026-04-01)
was last refreshed by hand. Both are imported by App.jsx.

**Fix:** add a monthly job (or a step in `update-polls.yml`) that runs
`python -m pipeline.fetch_economics` and the leaders refresh, with the same
commit-if-changed pattern.

## Cross-cutting improvements

1. **Silent failure is the theme.** A monthly job failed twice in a row and a
   second one no-ops with a green tick; nothing alerted anyone. Add a tiny
   scheduled health-check workflow that fails (and therefore emails the owner)
   when any tracked freshness stamp exceeds its budget, e.g.:
   `bludgertrack.retrieved` > 10 days, `betting_odds.source == "manual"`,
   `economics.generated` > 60 days, last `update-model-constants` run not
   successful. Alternatively add a `notify on failure` step to each workflow.
2. **`git diff --quiet` misses new files** in all four commit steps. Use
   `git add <paths> && git diff --cached --quiet && exit 0` instead.
3. **Add `concurrency:` groups** to the auto-committing workflows so the daily
   odds job and weekly polls job can't race each other's `git push` (the
   `pull --rebase` mitigates but doesn't eliminate this).
4. **`fetch-odds.yml` inconsistencies:** hardcodes `origin main` (others use
   `$GITHUB_REF_NAME`) and is the only auto-commit without `[skip ci]` — make
   the recursion/deployment behaviour deliberate and uniform once finding #4 is
   resolved.
5. **Actions runtime deprecation (time-sensitive):** every run currently warns
   that `actions/checkout@v4`, `actions/setup-python@v5`, `actions/cache@v4`
   run on Node 20, which is force-switched to Node 24 on **2026-06-16** and
   removed 2026-09-16. Bump to the current major versions this week.
6. **Stop patching App.jsx from CI.** `update-model-constants.yml` injects
   constants into the 10k-line `App.jsx` via regex (`inject_model_constants.py`)
   and auto-commits the result — a merge-conflict and corruption magnet. The
   state workflow already demonstrates the better pattern (separate generated
   data module); migrate `SEAT_RESIDUAL_MAP` / `SEAT_DEMO_MULT` etc. to
   `webapp/src/data/model_constants.js`.
7. **Document the automation.** CLAUDE.md describes `data/polls/` as "manually
   curated" and doesn't mention any of the four workflows; the deployment
   section describes a GitHub Pages pipeline that doesn't exist. Update both
   once the deploy path is confirmed.
